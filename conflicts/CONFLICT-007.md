# 衝突編號：CONFLICT-007

## 狀態：`detected`

## 衝突描述
- **市場開發者（既有 MDT 工作流）** 需要：依 market-development-tool v2.1 的成功指標,持續執行傳統產業客戶的潛在名單篩選、社群內容排程發布、銷售管道追蹤、市場洞察分析(每週至少 20 個合格名單、每月至少 5 則私訊詢問、90 天內 3 個初步洽談),這是一個 `done` 狀態下仍需持續運轉的營運型工作流
- **市場開發者（req 推廣執行者）** 需要:依 req-promotion-strategy 同時執行 (a) 雙語(en + zh-TW)內容產製與發布(NFR i18n + 成功指標 4 的 ≥1:1 比例) (b) 開發者社群外展與意見領袖關係經營(US-CC-001、CRM 開發者漏斗追蹤) (c) 品牌定位文件與 media kit 維護(US-MD-013、US-CC-002) (d) 90 天內促成 5 位意見領袖主動產出內容(成功指標 3) (e) 每封意見領袖外展訊息的人工 review(US-CC-001 與 US-MD-011 的「需要人工確認」)
- **為什麼衝突**:兩條工作流的執行者是同一個自然人(spec 擁有者親自署名)。spec 採用「深度共用」策略時假設「共用工具 = 共用人力槓桿」,但實際上工具的自動化只能降低執行成本,不能變出第二個市場開發者。新 spec 引入的工作項目在量級上與既有 MDT 同級(雙語 × 多平台 × 兩種 persona × 人工審核),且許多步驟(品牌定位文件審校、英文 README 母語潤飾、意見領袖個別研究、外展訊息人工 review)是無法被 content-generator 完全自動化的。在市場開發者每日工作時間有限的前提下,新 spec 的成功指標必然壓縮既有 MDT 的執行時間,造成兩個 spec 的成功指標互相搶資源。

## 衝突類型
**優先級／資源衝突**(同一執行者、有限時間、兩條並行的成功指標) + **跨 spec 排程衝突**(既有 done spec 的營運負載 vs 新 spec 的初期投入)

## 相關 User Stories / NFR
- 全部 req-promotion-strategy 的 US-MD-010 ~ US-MD-013(市場開發者作為執行者)
- US-CC-001 / US-CC-002:意見領袖外展與 media kit 維護工作量
- req-promotion-strategy 成功指標 1 ~ 4(尤其指標 4「英中比 ≥ 1:1」需要持續性的雙語產出)
- market-development-tool v2.1 成功指標 1 ~ 3(持續性的傳統產業客戶獲取)
- req-promotion-strategy 開放問題:「英文 README 由誰執筆或審校?(AI 草稿 vs 人工母語者潤飾)」— 此開放問題正是本衝突的具體表現
- research 決策 #4:深度共用 — 本衝突是「深度共用程式碼但無法深度共用人力」的反映

## AI 分析
這是 spec 沒有明確處理的「人」資源衝突,而非「程式碼」資源衝突。spec 的依賴關係章節討論了 content-generator、lead-scraper、Prisma models 的共用,但沒有任何章節討論市場開發者的時間如何在兩條工作流之間分配:

1. **人力 ≠ 程式碼**:深度共用 content-generator 可以降低開發成本,但內容仍需要審核、發布、追蹤回應、調整策略,這些都需要人。spec 在 US-MD-011 與 US-CC-001 都明確要求「需要人工確認」「需在發送前人工 review」,這些是無法被工具消除的時間成本。
2. **雙語 = 雙倍審核負擔**:成功指標 4「英中比 ≥ 1:1」意味著每篇內容需要審核兩次(英文版 + 繁中版),且英文版若由非母語者執筆,需要額外的潤飾與校對時間(這也是開放問題清單中的一項未決事項)。
3. **意見領袖工作的本質是高觸感**:US-CC-001 要求個人化外展、引用對方作品、提供 exclusive 資訊,US-CC-003 要求每封訊息中立化人工審查。每位意見領袖的「研究 → 草擬 → 審核 → 寄送 → 追蹤回應 → 後續關係維護」是 hours 級的工作,而非 minutes。成功指標 3 要 90 天內 5 位主動產出內容,意味著外展漏斗至少需要 30 ~ 50 位候選(典型轉化率 10%),這是顯著的人工負載。
4. **既有 MDT 的營運慣性**:MDT v2.1 的成功指標是「每週」「每月」「90 天內」的持續性指標,而非一次性目標,這代表市場開發者已經將部分時間鎖定在 MDT 的營運循環中。新 spec 沒有討論「為了執行 req 推廣需要從 MDT 借多少時間」「借走的時間是否會讓 MDT 指標下降」「下降是否可接受」。
5. **與 CONFLICT-006 的耦合**:若 CONFLICT-006 走方案 3(每封意見領袖外展訊息人工 review),會直接放大本衝突的嚴重性 — 人工 review 的時間成本會在 5 ~ 50 位候選的尺度上線性放大。
6. **與品牌定位文件的耦合**:US-MD-013 的品牌定位文件要由 spec 擁有者親自拍板與維護(開放問題中已標記「三個 USP 需要在 /req-plan 之前由 Spec 擁有者拍板」),這是另一段不可委派的高品質時間需求。
7. **無新增 persona 來分擔**:research 決策 #2 明確「不含 B 貢獻者招募」,所以這個 spec 沒有任何機制讓社群幫忙分擔工作量;所有負載都落在市場開發者一人身上。

## 解決方案
- [ ] 方案 1:**明確時間分配比例 + 接受 MDT 指標暫時下調**(優先滿足新 spec 的初期推廣動能)。在 spec 中加入新章節「執行者時間配置」,明定「未來 90 天內市場開發者投入 req 推廣的時間佔比 X%、MDT 維運佔 (100-X)%」,並同步更新 MDT spec 的成功指標備註,允許在這 90 天內 MDT 的「每週 20 個名單」「每月 5 則私訊」指標下調至 X%。代價:需透過 `/req-iterate` 修改 MDT spec 的成功指標,且代表既有 MDT 的營收/客戶獲取會在這段期間放緩,需 spec 擁有者承擔商業風險。
- [ ] 方案 2:**自動化強化 + 人工審核分級**(優先滿足兩個 spec 的指標,降低單位工作量)。將 content-generator 的人工確認流程依風險分級:低風險(如 README 段落改寫、翻譯校對)只需 batch review,高風險(意見領袖外展訊息、品牌定位文件變更)維持單筆 review。同時擴張 lead-scraper 的自動化過濾規則,將意見領袖候選名單的初步篩選由人工降為自動,只在 top 10 的最終決定階段才人工介入。代價:低風險自動化仍可能漏出品質問題;高風險人工瓶頸仍存在;且依然無法完全消除時間衝突,只是延後爆發。
- [ ] 方案 3:**分階段排程 — 先 MDT 後 req 推廣,序列化執行**(折衷方案)。將 req 推廣 spec 切成兩個階段:Phase 1(0 ~ 30 天)只執行品牌定位文件、英文 README、media kit 等「一次性建置」工作,完全不啟動意見領袖外展;Phase 2(31 ~ 90 天)才開始外展與雙語內容排程。Phase 1 期間 MDT 維運不受影響;Phase 2 才有時間衝突,但屆時 Phase 1 的成果(README、media kit)已可承擔部分被動曝光,降低 Phase 2 的主動外展強度。代價:成功指標 3「90 天內 5 位意見領袖」會壓縮到 60 天內達成,實際難度上升;且需在 spec 中新增階段化里程碑章節。
